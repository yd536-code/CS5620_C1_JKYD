# Scene

Core scene graph: model graph, scene model, scene view, scene controller, and supporting types. Scene views and controllers come in backend-agnostic abstract bases (`ASceneView`, `ASceneController`) with concrete Three.js (`AGL*`) and Two.js (`ATwoJS*`) subclasses.

The four top-level pieces form the running application: `AModelGraph` is the actual tree of `ANodeModel`s (see [./nodeModel/](./nodeModel/README.md) for the base node-model classes and [./nodes/](./nodes/README.md) for the concrete node types built on them), and fires `SCENE_NODE_ADDED`/`REMOVED`/etc. events as it changes; `ASceneModel` owns one or more named `AModelGraph`s plus a shared camera model ([./camera/](./camera/README.md), typed to `CameraModelInterface & ANodeModel`; the 2D and 3D starter scene models narrow the `cameraModel` accessor to `ACameraModel2D` / `ACameraModel3D`) and coordinates asynchronous asset/scene setup (see "Scene Initialization" below); `ASceneView` maps a model graph to a parallel tree of node views (see [./nodeView/](./nodeView/README.md)) via a per-scene class map, letting different node model types render through different view classes; and `ASceneController` is the top of the stack — it owns the scene model and view, drives the render/update loop, handles resize, and manages the active [./interactionmodes/](./interactionmodes/README.md) that turn user input into scene changes. Lighting nodes live in [./lights/](./lights/README.md). Everything above the `AGL*`/`ATwoJS*` split is backend-agnostic; concrete apps are built from a Three.js or Two.js scene controller subclass (see [../starter/](../starter/README.md) for the reusable starting points) rather than from these bases directly.

## Contents:
- [./__tests__/](./__tests__/README.md): Unit tests for the scene module.
- [./camera/](./camera/README.md): Camera model and view for controlling the scene's viewpoint.
- [./interactionmodes/](./interactionmodes/README.md): The base `ASceneInteractionMode` used by scene controllers on both backends.
- [./lights/](./lights/README.md): Light model and view classes (abstract light, point light, visible point light).
- [./nodeModel/](./nodeModel/README.md): Node model base classes for 2D and 3D scene graph nodes.
- [./nodeView/](./nodeView/README.md): Node view base classes (abstract `ANodeView`, Three.js `AGLNodeView`) and group node views.
- [./nodes/](./nodes/README.md): Concrete node model/view pairs for triangle meshes, loaded assets, 2D geometry, and unit quads.
- [./AModelGraph.ts](./AModelGraph.ts): The root node of a scene's model hierarchy. Maintains a flat `modelMap` of all descendant models and fires events when nodes are added, removed or released. Adding a node registers it and all of its descendants, in preorder, firing `NodeAdded` for each, so a subtree built before it joined the scene gets a view for every node. Each registered model is removed from `modelMap` and fires `NodeReleased` exactly once when it is released, even if it was detached from the graph first.
- [./ARenderPass.ts](./ARenderPass.ts): One entry in a scene controller's render list -- a scene view, camera model, viewport, clear flags, and optional render target. `AGLSceneController.renderPasses()` runs an ordered list of these; a single-pass scene gets one automatically. Three.js/AGL only -- Two.js has no equivalent. It also has `localNDCCursor`/`worldPointAtCursor` (a pass's own re-normalized NDC and world-point lookup, through its own camera), and the file has the free function `findPassAtCursor` (front-to-back pass hit-testing).
- [./ASceneController.ts](./ASceneController.ts): Abstract scene controller base (both backends). Bridges the scene model and scene view, coordinates initialization, handles window resize, and owns interaction modes (`createNewInteractionMode`). `initSceneViews` and `getWorldCoordinatesOfCursorEvent` are implemented here and shared by both backends.
- [./AGLSceneController.ts](./AGLSceneController.ts): Three.js scene controller. Manages scene views and render targets for multi-pass rendering, the camera view, and default model-view specs, plus the render-pass list (`renderPassList`, `addRenderPass`, `renderPasses()`) and pass-aware camera/view lookup (`getThreeJSCamera`, `getViewListForModel`, `cameraViewForPass`, all taking an optional `ARenderPass`). Also `getPassAtCursor` (front-to-back pass hit-testing) and a pass-aware `getNodeViewAtCursor` (an optional `ARenderPass` argument raycasts against that pass's own camera/scene and pass-local NDC; without it, it uses the main camera and canvas-wide NDC).
- [./ATwoJSSceneController.ts](./ATwoJSSceneController.ts): Two.js scene controller. Manages one `ATwoJSSceneView` per model graph and wires the Two.js render loop (see file header for the full initialization sequence).
- [./ASceneModel.ts](./ASceneModel.ts): Abstract scene model. Contains one or more `AModelGraph` instances, a camera model, and asset management. Coordinates asynchronous initialization via a mutex.
- [./ASceneView.ts](./ASceneView.ts): Backend-agnostic scene view base. Owns the model→view map, the model-class→view-class registry (`classMap`/`addModelViewSpec`/`defaultViewClass`), and the bookkeeping built on them (`hasModel`, `hasView`, `addView`, `getViewListForModel`, `disposeViews`, `release()`, `onModelNodeReleased`); also defines the `SceneControllerSubscriptions` enum. `onModelNodeReleased` calls `.release()` (not just `.dispose()`) on every view of the released node, so the views' model listeners are removed too. `removeView`/`releaseView`/`onModelNodeAdded`/`onModelNodeRemoved`/`addNodeViewToRoot` are abstract, because each backend does them differently.
- [./AGLSceneView.ts](./AGLSceneView.ts): Three.js scene view. Owns the `THREE.Scene` and the Three.js-specific pieces of view creation/attachment; the model↔view-class bookkeeping itself lives on `ASceneView` (see above).
- [./ASceneViewsAndTargets.ts](./ASceneViewsAndTargets.ts): Container grouping `AGLSceneView` instances with `ARenderTarget` objects, supporting multi-pass rendering setups.
- [./ConfirmInitialized.ts](./ConfirmInitialized.ts): Interface requiring `initMutex` and `confirmInitialized()` for async lazy initialization guarded by a mutex.
- [./QuickNodeView.ts](./QuickNodeView.ts): Convenience node view that accepts `init`, `update`, and `dispose` callbacks at construction time rather than requiring a subclass.
- [./index.ts](./index.ts): Barrel export for the scene module.

### Scene Initialization
Both the model and controller take part in initialization, and each guards it with a mutex so it runs only once. The controller's `confirmInitialized()` first awaits the model's `confirmInitialized()`: the model preloads assets, calls `initCamera`, then awaits `initScene` (which may be `async`), and only then counts as initialized and starts its clock. The controller then runs `initSceneViews()`, `initModelViewSpecs()` and `initRendering()`, and starts its own clock. The promise the controller's `confirmInitialized()` returns resolves after all of this has finished.
